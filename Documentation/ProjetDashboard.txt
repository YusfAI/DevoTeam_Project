Ce que ton projet fait
L’utilisateur écrit une demande en langage naturel, le chatbot interprète l’intention, puis le LLM transforme cette intention en une structure de dashboard, et enfin un moteur de rendu produit le dashboard dans le site web. Des travaux récents montrent que la génération de dashboards interactifs est difficile dès qu’on veut reproduire la logique d’interaction, pas seulement le visuel, donc il faut prévoir une étape de validation et de contrôle qualité dès le départ.

Choix techniques
Pour le LLM, je te conseille de viser un modèle open source qui a un bon équilibre entre qualité et coût d’exécution, idéalement via un serveur local compatible API. Dans ton cas, le plus important n’est pas juste la taille du modèle, mais sa capacité à produire des sorties structurées et cohérentes pour une tâche de génération de code ou de schéma.

Pour la visualisation, Vega est pertinent parce qu’il formalise le dashboard en JSON avec data, scales, axes, marks et signals, ce qui facilite la génération automatique et le rendu côté client. Pour les données, SQLite est suffisant au début, surtout si ton application est locale ou à faible charge, et plusieurs projets montrent que ce type d’architecture peut rester léger et pratique.

Plan de conception
Le meilleur plan est de découper ton projet en blocs fonctionnels :

Bloc 1: compréhension du besoin. Le chatbot extrait l’objectif utilisateur, par exemple “je veux suivre les ventes par mois avec filtre pays”.

Bloc 2: normalisation. Le LLM transforme le texte en une structure métier standard.

Bloc 3: décision dashboard. Le système choisit le bon type de graphiques et widgets.

Bloc 4: génération Vega. Un module produit le JSON Vega.

Bloc 5: exécution et affichage. Le navigateur lit le JSON et affiche le dashboard.

Bloc 6: sauvegarde. SQLite conserve les données, les préférences et l’historique.

Comment le rendre intelligent
Pour que ton système donne “le bon dashboard”, il faut définir une couche intermédiaire entre le texte utilisateur et Vega. Cette couche peut être un JSON métier du genre: objectif, métriques, dimensions, filtres, période, niveau de détail, style visuel, interactions attendues. Ensuite seulement tu convertis ce JSON vers Vega.
vega

Exemple simple: si l’utilisateur dit “montre-moi les ventes par mois avec un filtre par pays”, le LLM ne doit pas répondre directement avec un chart brut. Il doit d’abord sortir quelque chose comme: métrique = ventes, dimension temporelle = mois, filtre = pays, visualisation = line chart, interactions = dropdown pays, puis le générateur Vega crée le dashboard.
vega

Risques à éviter
Le premier risque est de laisser le LLM générer du code sans schéma imposé, ce qui crée des sorties incohérentes. Le deuxième risque est de vouloir tout faire d’un coup: compréhension, génération, rendu, logique métier, design, et stockage, sans étapes intermédiaires.
antonioarcher

Le troisième risque est de dépendre trop vite d’un seul modèle open source sans évaluation. Les résultats récents montrent qu’il existe encore un écart important entre modèles open source et systèmes plus puissants sur les tâches de dashboard dynamique, donc il faut prévoir des tests dès le début.
